# Compatibility and validation

The Windows prototype reaches the title screen with a native boot module. The USA revision 0 idle fix restored normal speed in the early-boot benchmark. The local disc pair has been identified and hashed.

| Area | Evidence |
| --- | --- |
| Public source project | Available on GitHub with source CI. |
| Recompiler/runtime build | DolRecomp, ModernGekko, the disc conversion tool and Windows launcher built locally. |
| Disc identity and revision validation | Both discs: GGSEA4, revision 0; main executables have identical SHA-256. Full normalized-disc hashes recorded in supported-builds.json. |
| Native game module | Local setup built one shared native boot module. Both discs share the same main REL. The reconstructed REL executable bytes matched seven local checkpoints and fresh boots of both discs. The full experimental module linked and ran verified REL code during gameplay. It reached about 42% of normal speed on a headless gameplay replay, with about 71% of the busiest thread's CPU samples in native module code. |
| Experimental LLVM backend | The Windows x64 return fix preserved `XMM7` across the CPU run loop. Gameplay and cutscene replays shut down normally and reached 49% and 73% of normal speed, respectively, with output disabled. The regular build uses the C backend. |
| x64 fallback linking | The linked build reached 100% median speed on two earlier headless gameplay replays, compared with about 84% for the reference. At the new F1 checkpoint, headless hybrid speed rose from 79.7% to 98.6% and fullscreen Vulkan at 4× rose from 82.6% to 98.6%. The JIT reference reached 100%. The source build now includes the linking change for eligible fixed-range modules. Pacing dips and a complete live playthrough still need validation. |
| Experimental separate CPU and video threads | The tester reported smooth live play in the isolated profile. In matched 30-second Vulkan replays at 4× fullscreen with sound enabled, both configurations reached 99.9% median game speed. The speed floor improved from 70.3% with one thread to 95.7% with separate threads. Each run still logged a gap in rendered frames. Later gameplay, cutscenes and audible playback remain pending. |
| Boot / gameplay | Disc 1 reached the main menu at about 60 FPS with the idle fix. Disc 2 advanced at normal speed in a headless boot test. Disc 1 entered gameplay, with a pre-fix live capture ranging from 15.8 to 27.1 FPS. The current boot-only build reached 74–75% of normal speed in two headless replays of the same gameplay checkpoint. The main REL uses JIT fallback in this build. |
| Audio / cutscenes / codec | Scripted input opened the codec and displayed a Campbell conversation. Headless hybrid and JIT replays generated identical DSP audio across 28.3 seconds of the same dialogue checkpoint. Matched 18-second Windows captures at 4× internal resolution reported zero packet discontinuities in JIT and in both hybrid threading modes. The shared-thread hybrid run dipped to 90.6% game speed and the separate-thread run to 98.6%. Audible playback across later scenes still needs verification. |
| Controller | The fixed Windows runtime automatically assigns a physical XInput controller to port 1. The trace captured Start, A, B and D-pad presses, and the tester confirmed an in-game response. A later Windows test showed the game falling back to the keyboard on disconnect and reassigning the controller to port 1 on reconnect without a restart. The updated runtime also assigned the pad in a fresh test profile with a zero-byte controller config. Other controller types still need hardware testing. |
| Windows window shutdown | A live restart returned `0xC000041D` when Windows delivered a window callback after the configuration had been shut down. An isolated Win32 test reproduced the code by delivering focus loss during teardown. The patched window detached its platform and exited normally in the same test. The patched runtime also exited cleanly after closing a live game window. |
| Concurrent launches | A two-process Windows launcher test used separate data directories and stubbed the game subprocess. It rejected a second visible session with exit code 24, accepted it after the first ended, and allowed isolated headless diagnostics. The staged dev.10 Windows executable also returned 24 before starting the runtime when the shared lock was held. |
| Guest CPU error during dock replay | One isolated Vulkan test with separate CPU and video threads reached a non-code guest address while resuming during a guard alert. The automation reload had yet to report completion. Scripted hybrid and JIT replays reached the same area and reloaded successfully. Repeated hybrid resume and reload tests completed 15 cycles with separate threads and 15 with shared threading without the error. The cause remains open. |
| Save / load / disc transition | The hybrid build read two USA memory-card fixtures and loaded their carryover inventory. Its Save Photo menu wrote a new 24,640-byte card file. After restarting, Photo Album displayed the new photograph correctly with external framebuffer copies to guest memory enabled. The normal graphics profile produced a magenta thumbnail. The manifest exposes a separate Photo Album capture setting. Local save-state replay works. The linked runner booted each disc and mounted the other on a drive command. Writing and reloading a story-progress save and the story-driven disc swap remain open. [Community memory-card fixture](https://gc-saves.com/container/329) |
| Save preservation during setup and repair | In a disposable install with spaces in its path, the dev.9 and dev.11 packaged launchers prepared both discs using bundled tools. The dev.11 setup rebuilt an intentionally emptied native module even though its completion marker was present. Both discs booted from the repaired module and shut down normally. The memory-card fixture and display settings were byte-identical across the update and repair. The in-app RecompLauncher update path still needs testing. |
| Windows paths with non-ASCII characters | Dev.12 could inspect both discs, then failed extraction because DolRecomp lost characters in the path. The dev.13 local package used both patched Windows executables to prepare ISO inputs with accented filenames inside a folder with CJK characters and spaces. Compilation used bundled tools from a Windows system-only `PATH`. A repeat setup preserved the native module's hash and modification time. Both discs booted headlessly from the prepared data directory, dispatched native code, mounted the other disc on an explicit test command, and shut down normally. |
| Complete playthrough | Not tested |
| RecompLauncher schema | Passes the official current schema; separate disc inputs and prepare/start entry points. |
| RecompLauncher installed-package test | RecompLauncher beta 68 imported a local package, accepted both RVZ files, and reached Ready to Play after setup built the shared native module. Game Settings wrote borderless fullscreen and 4× into the local settings file. The updated package prepared both discs using bundled tools with a system-only `PATH`, verified both normalized disc hashes, and reused the build on repeat. It rejected reversed inputs and preserved the prepared build. Running the manifest's start command directly with the saved display settings loaded the native boot module, opened a 2560 × 1440 client area, and recorded eight startup samples at 100% game speed. The dev.10 package also reached the title screen headlessly with an existing test profile. Play through the launcher, Big Picture inside the app and a clean Windows account test remain pending. |
| Monitor-native fullscreen / higher internal resolution | Startup, toggling and three controlled minimize and restore cycles produced a 2560 × 1440 fullscreen client area. The tester previously observed a maximized window after restoring. The updated runner followed the launcher mode for automatic fullscreen and honored both explicit overrides. With separate CPU and video threads it reached 99.9% median game speed in 30-second fullscreen Vulkan replays at both 1× and 4×. Other monitors, DPI settings, HUD placement and effects still need validation. |
| Unlocked frame rate | The scheduler and framebuffer copy traces measured about 30 updates per second in a dialogue checkpoint and 60 in gameplay. The same viewport setup call followed those rates, and controller polling ran at 59.94 Hz in both. The startup movie task ran about 30 times per second in its replay. Camera and animation evaluation and decoder output cadence still need verification. The test build uses the original game timing. |

Do not interpret an instruction translation percentage, a successful host build, a boot screen or a launcher schema check as full game compatibility.
