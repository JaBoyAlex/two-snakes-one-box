# Compatibility and validation

The Windows prototype reaches the title screen with a native boot module. The USA revision 0 idle fix restored normal speed in the early-boot benchmark. The local disc pair has been identified and hashed.

| Area | Evidence |
| --- | --- |
| Public source project | Available on GitHub with source CI. |
| Recompiler/runtime build | DolRecomp, ModernGekko, the disc conversion tool and Windows launcher built locally. |
| Disc identity and revision validation | Both discs: GGSEA4, revision 0; main executables have identical SHA-256. Full normalized-disc hashes recorded in supported-builds.json. |
| Native game module | Local setup built one shared native boot module. Both discs share the same main REL. The reconstructed REL executable bytes matched seven local checkpoints and fresh boots of both discs. The full experimental module linked and ran verified REL code during gameplay. It reached about 42% of normal speed on a headless gameplay replay, with about 71% of the busiest thread's CPU samples in native module code. |
| Experimental LLVM backend | The Windows x64 return fix preserved `XMM7` across the CPU run loop. Gameplay and cutscene replays shut down normally and reached 49% and 73% of normal speed, respectively, with output disabled. The regular build uses the C backend. |
| x64 fallback linking | The linked build reached 100% median speed on two earlier headless gameplay replays, compared with about 84% for the reference. At the new F1 checkpoint, headless hybrid speed rose from 79.7% to 98.6% and fullscreen Vulkan at 4× rose from 82.6% to 98.6%. The JIT reference reached 100%. The source build now includes the linking change for eligible fixed-range modules. Pacing dips and a complete live playthrough still need validation. |
| Experimental separate CPU and video threads | The tester reported smooth live play in the isolated profile. In four matched warm-cache dev.18 Tower A replays at 4× Vulkan, separate threads reduced samples below 95% game speed from 57 to 33 out of 562 per mode. One separate-thread run had seven VBlank gaps over 50 ms, with a maximum of 99.93 ms. The shared runs had one gap over 50 ms. The launcher defaults to shared threads while the long gaps and earlier guest fault remain open. |
| Boot / gameplay | Disc 1 reached the main menu at about 60 FPS with the idle fix. Both discs advanced at 100% median game speed in headless boot tests with the cache and dispatch patch. Disc 1 entered gameplay, with a pre-fix live capture ranging from 15.8 to 27.1 FPS. An earlier boot-only build reached 74–75% of normal speed in two headless replays of the same gameplay checkpoint. The regular build uses JIT fallback for the main REL. |
| Audio / cutscenes / codec | Scripted input opened the codec and displayed a Campbell conversation. Headless hybrid and JIT replays generated identical DSP audio across 28.3 seconds of the same dialogue checkpoint. In dev.14, Windows loopback reported zero packet discontinuities across the Tower A alarm, Hind fight and Underground Passage flashback replays with Vulkan at 4×. The Hind fight and flashback reached 100% median game speed. The flashback had a 66.7 ms 95th-percentile render interval in both hybrid and JIT, so that interval alone cannot identify a slowdown. Listening tests under sustained load remain open. |
| Short Tower A replays | Two normal 4× Vulkan windowed replays with sound reached 99.2–99.9% median game speed with the filtered cache hook, compared with 91.3–94.2% on dev.15. The patched runs dipped to 89.6% and 95.2%, with longest render intervals of 36.02 ms and 36.46 ms. |
| Sustained dev.16 replays | Heliport held 100.0% median game speed for 75 seconds. A 90-second Tower A replay measured 96.3% median and 71.9% minimum with shared-thread hybrid execution. Separate threads reached 100.0% median and 92.1% minimum. JIT reached 100.0% median and 99.5% minimum. All four windowed 4× Vulkan captures recorded zero Windows audio packet discontinuities. The shared-thread Tower A slowdown remains reproducible. |
| Register synchronization | The x64 candidate reached 98.6–98.8% median speed in matched 90-second Tower A replays, compared with 94.5–96.8% on dev.16. Samples below 95% fell from 329 of 720 to 133 of 720. The candidate still dipped to 60.3% and logged a 103.24 ms vertical blank interval in one run. A headless repeat matched 273 sampled dev.16 dispatch records and 22.333 seconds of DSP audio. The isolated dips remain open. |
| Shader cache and hitches | Standalone startup now creates the shader cache path. A fresh profile wrote six Vulkan cache files, and a restart read 34 saved pipeline UIDs. One warm replay had a 73.66 ms VBlank gap that included a 55.4 ms Vulkan fence wait. Two warm repeats reached 100.0% median game speed. The longer repeat gap was 78.91 ms, with no overlapping wait in the renderer probes. The origin of the earlier fence wait and the remaining intermittent gaps still need investigation. |
| Windows thread scheduling | Two 85-second Tower A runs at normal priority had VBlank gaps up to 48.45 and 60.07 ms. Two private above-normal trials peaked at 35.59 and 32.80 ms. The combined CPU and video thread showed fewer ready-to-run snapshots during long gaps. One priority trial still ran at 89.8% median game speed. A separate profile during sustained slowdown identified the native game module and instruction fallback hook as CPU targets. |
| Cache-flush CPU cost | The new inlined translation path matched the original MMU on 3,295,835 sampled cache-flush lookups over Heliport and Tower A. In matched headless Tower A replays it reduced emulation-thread CPU cost per update from 16.65–16.91 ms to 16.01–16.18 ms. Both 70-second 4× Vulkan candidate replays reached 100% median game speed. The dev.18 controls ranged from 97.3% to 100%, and isolated frame gaps still varied. |
| Dev.19 package startup | The rebuilt dev.19 runner, with the cache verifier removed, booted both discs headlessly through `TwinSnakes.exe` with a system-only `PATH` and prepared data. Both boots loaded the native module, dispatched native code and exited normally. |
| Dev.20 package and gameplay checks | A fresh portable package accepted both RVZ files with accented names from a path containing CJK characters. Setup verified the discs and built one shared native module using only the bundled tools on a system-only `PATH`. Both discs booted headlessly through `TwinSnakes.exe`, dispatched native code and shut down normally. The Disc 2 Vulcan Raven checkpoint ran for 30 seconds in offscreen 4× Vulkan at 100% median game speed, with a 98.0% minimum. |
| Dev.21 package startup | A fresh setup through `TwinSnakes.exe` on a system-only `PATH` used the bundled tools to verify both RVZ files and build the shared native module. Each disc booted headlessly, advanced at least 80 presents and shut down normally with native dispatch recorded. |
| Dev.20 sustained Tower A | A 75-second windowed replay with warm shader caches, 4× Vulkan and Cubeb reached 100% median and 81.4% minimum game speed. Seven of 301 samples fell below 95%. The largest render and VBlank intervals were 46.31 ms and 43.74 ms. |
| Dev.20 Direct3D comparison | Matching warm-cache 75-second replays at 4× reached 100% median speed with zero samples below 95% on Direct3D 11 and Direct3D 12. The longest VBlank intervals were 34.19 ms and 25.88 ms, respectively. The comparison used one checkpoint on a GeForce RTX 3060 Ti. [Measurements](PERFORMANCE.md#dev20-tower-a-graphics-backends) |
| Dev.19 gameplay and audio | Four 22-second replays with 4× Vulkan and Cubeb on the rebuilt package reached 100% median game speed with zero reported Windows audio packet discontinuities. These covered Tower A, the Underground Passage flashback and two Hind fight runs. The longest VBlank interval was 37.47 ms, and the Tower A speed dipped to 85.55%. The 69.05 ms Hind fight gap from the initial package did not recur. Listening and sustained gameplay tests remain open. [Measurements](PERFORMANCE.md#dev19-packaged-gameplay-and-audio) |
| Dev.19 sustained Tower A | Three 75-second warm-cache replays at 1×, 4× and 1× Vulkan all reached 100% median game speed. Samples below 95% were 8, 7 and 5 out of about 300 in each run. The first 1× run had a 56.04 ms maximum VBlank interval while a package-digest check was ending. The 1× repeat peaked at 43.92 ms. [Measurements](PERFORMANCE.md#dev19-packaged-gameplay-and-audio) |
| Dev.19 scheduling follow-up | At 1×, the emulation thread was ready to run in 23% of snapshots during long VBlank gaps in two diagnostic runs, compared with 0.26% outside those gaps. Two above-normal priority trials peaked at 31.68 and 25.39 ms. The final normal-priority control peaked at 26.72 ms and had zero samples below 95% game speed. The release profile uses normal priority. [Measurements](PERFORMANCE.md#dev19-scheduling-at-default-internal-resolution) |
| x64 condition-register packing | Two matched Tower A comparisons reduced emulation-thread CPU cost by 1.4–3.0% per video update. A Disc 1 dialogue replay produced 23.448 seconds of matching DSP samples, and the SSE2 implementation matched the original scalar rules on one million test inputs. [Measurements](PERFORMANCE.md#x64-condition-register-synchronization) |
| Controller | The fixed Windows runtime automatically assigns a physical XInput controller to port 1. The trace captured Start, A, B and D-pad presses, and the tester confirmed an in-game response. A later Windows test showed the game falling back to the keyboard on disconnect and reassigning the controller to port 1 on reconnect without a restart. The updated runtime also assigned the pad in a fresh test profile with a zero-byte controller config. Other controller types still need hardware testing. |
| Windows window shutdown | A live restart returned `0xC000041D` when Windows delivered a window callback after the configuration had been shut down. An isolated Win32 test reproduced the code by delivering focus loss during teardown. The patched window detached its platform and exited normally in the same test. The patched runtime also exited cleanly after closing a live game window. |
| Windows IOS filesystem metadata | Holding the existing `fst.bin` without delete sharing reproduced the startup rename warning in a disposable profile. The updated runner retried the atomic replacement and booted normally after the lock was released. Native controls holding the source or destination lock through all retries preserved both files and succeeded after release. A lock that prevents writing the temporary file fails before the rename step. |
| Concurrent launches | A two-process Windows launcher test used separate data directories and stubbed the game subprocess. It rejected a second visible session with exit code 24, accepted it after the first ended, and allowed isolated headless diagnostics. The staged dev.10 Windows executable also returned 24 before starting the runtime when the shared lock was held. |
| Guest CPU error during Dock replay | One isolated Vulkan test with separate CPU and video threads reached the disc metadata region while resuming during a guard alert. A reload request was still pending. Dev.21 reported no instruction errors over 60 further cycles using the original harness. With the harness waiting for actual load results, a follow-up completed 45 separate-thread hybrid cycles using the original pending checkpoint, 45 shared-thread hybrid cycles and 25 shared-thread JIT cycles. All three used offscreen Vulkan and exited normally. The original guest fault did not recur. |
| Save-state automation results | Dev.21 marked missing, truncated and wrong-disc save loads as processed after enqueueing them. The updated runner reports failure for each case and marks valid loads processed after restoration on the CPU thread. A paused Dock round trip restored the same 6 MiB RAM sample byte for byte. A valid load while running continued to present frames. |
| Save / load | The dev.13 hybrid run advanced from the Cargo Dock to the Heliport, then wrote a new 24,640-byte story save through Mei Ling's Codec menu. A fresh process loaded the card file from the title menu and returned to the Heliport with the saved equipment. The seeded card file remained byte-identical. Repeat packaged RVZ setup in a separate data directory also preserved a copy of the new story save byte for byte. Photo Album displayed a previously saved photograph after restart with external framebuffer copies to guest memory enabled. The normal graphics profile produced a magenta thumbnail. The manifest exposes a separate Photo Album capture setting. Local save-state replay works. [Community memory-card fixture](https://gc-saves.com/container/329) |
| Automatic Disc 2 handoff | Dev.13 mounted Disc 2 but stopped producing game frames after reading its header. Extracted Disc 1 overwrote the original file-table capacity of 29,340 bytes with its own 29,148-byte table size. Disc 2 needs the full 29,340 bytes. Dev.14 preserves that capacity. In a headless run launched through the packaged `TwinSnakes.exe`, entering the Underground Passage door triggered an automatic mount, read the Disc 2 file table, and entered Communication Tower A. Loading a Tower A save from Disc 1 also triggered the swap. A Disc 1-only control stayed on the game's disc prompt. After the swap, Mei Ling wrote a new 24,640-byte story save and preserved the source save. A fresh Disc 2 boot loaded the new save and resumed movement. The rebuilt dev.19 package repeated the swap from the Disc 1 title menu by loading the Tower A card save, advanced another 300 frames after the handoff, and exited normally. The door route was verified on dev.14. [USA practice saves](https://www.speedrun.com/mgstts/resources/z3thf) [End of Disc 1 checkpoint](https://gbatemp.net/threads/nintendont-savegames-upload-sharing.370846/#post-5170899) |
| Dev.19 story door and save restart | The packaged launcher cold-booted Disc 1 and resumed a local save state just outside the Underground Passage door. Scripted movement through the door triggered the Disc 2 mount and preserved the 29,340-byte file-table capacity. The test entered Tower A, advanced another 308 frames and created a new 24,640-byte save through Mei Ling. A fresh Disc 2 process using the same data directory loaded Communication Tower A from the new card entry and resumed movement. Both card files stayed byte-identical across restart. A separate cold attempt loaded an end-of-Disc-1 card save and played the corridor cutscene. Its scripted movement ended short of the door. |
| Save states and disc identity | Dev.19 applied a Disc 2 Hind checkpoint while Disc 1 remained mounted. The updated runtime records the mounted disc in new Twin Snakes save states. It rejected the new Disc 2 state on Disc 1 and gameplay continued. After mounting Disc 2, a new state recorded Disc 2. A fresh Disc 2 boot loaded a tagged checkpoint, and the original Disc 2 fixture still loaded with its matching disc. The earlier Dock fault occurred on a single disc and remains unexplained. |
| Save preservation during setup and repair | In a disposable install with spaces in its path, the dev.9 and dev.11 packaged launchers prepared both discs using bundled tools. The dev.11 setup rebuilt an intentionally emptied native module even though its completion marker was present. Both discs booted from the repaired module and shut down normally. The memory-card fixture and display settings were byte-identical across the update and repair. The in-app RecompLauncher update path still needs testing. |
| Repair of damaged cached files | In a disposable portable package, the previous setup reported `Already built` with a corrupted Disc 1 executable and a corrupted, nonempty native DLL. The updated setup re-extracted Disc 1 and rebuilt the shared DLL. Repeat setup verified both executables and the DLL digest, then reused the build. Both discs booted with native dispatch and exited normally. The card save and display configuration stayed byte-identical. |
| Windows paths with non-ASCII characters | Dev.12 could inspect both discs, then failed extraction because DolRecomp lost characters in the path. The dev.13 local package used both patched Windows executables to prepare ISO inputs with accented filenames inside a folder with CJK characters and spaces. Compilation used bundled tools from a Windows system-only `PATH`. Repeat setup preserved the native module's hash and modification time. Setup also converted both RVZ inputs in the same folder, verified the normalized disc hashes and reused the build. Both discs booted headlessly from the prepared data directory, dispatched native code, mounted the other disc on an explicit test command, and shut down normally. |

| Interrupted native compilation | An isolated dev.19 test ran the manifest's prepare command and used beta 68's Windows process-tree cancellation during step 2 of 35. The previous prepared record, settings and card save stayed byte-identical. No new completion record was written. | Dev.19 package inventory | All 20,618 indexed files matched their staged hashes. The inventory excluded local player data, disc images, game modules, saves and logs. Corresponding-source and third-party notice review remains a release gate. |
| Monitor-native fullscreen / higher internal resolution | Startup, toggling and three controlled minimize and restore cycles produced a 2560 × 1440 fullscreen client area. The tester previously observed a maximized window after restoring. The updated runner followed the launcher mode for automatic fullscreen and honored both explicit overrides. With separate CPU and video threads it reached 99.9% median game speed in 30-second fullscreen Vulkan replays at both 1× and 4×. Other monitors, DPI settings, HUD placement and effects still need validation. |
| Unlocked frame rate | The scheduler and framebuffer copy traces measured about 30 updates per second in a dialogue checkpoint and 60 in gameplay. The same viewport setup call followed those rates, and controller polling ran at 59.94 Hz in both. The startup movie task ran about 30 times per second in its replay. Camera and animation evaluation and decoder output cadence still need verification. The test build uses the original game timing. |

Do not interpret an instruction translation percentage, a successful host build, a boot screen or a launcher schema check as full game compatibility.
